# WAVEON BUSAN

AI로 부산 해양레저 상품을 추천하고, 계약서를 미리 이해한 뒤 모두싸인 전자서명까지 진행하는 구매자·판매자 통합 웹서비스입니다.

## 문제와 해결 방식

해양레저 현장에서는 장비를 착용한 직후 복잡한 면책·환불 약관에 급하게 서명하는 일이 많습니다. 외국인 관광객과 미성년자는 언어와 절차 때문에 계약 내용을 충분히 이해하기 더 어렵고, 판매자도 계약 발송·상태 확인·증빙 보관을 따로 관리해야 합니다.

WAVEON BUSAN은 이 흐름을 예약 단계로 앞당깁니다.

1. 사용자의 예산, 동행, 수영 여부, 경험과 선호를 바탕으로 부산 해양레저 상품을 추천합니다.
2. 실제 계약서 PDF에서 요금·기간·환불·안전·보상 및 책임 조항을 구조화합니다.
3. 불리할 수 있는 조항을 쉬운 말로 요약하고 한국어·영어·일본어·중국어 번역을 제공합니다.
4. 판매자가 계약서를 검토·수정해 구매자 웹 알림과 이메일로 보냅니다.
5. 구매자는 웹 안에서 모두싸인 전자서명을 진행하고, 양쪽 마이페이지에서 상태와 체결 문서를 확인합니다.

## 사용자와 핵심 기능

| 사용자 | 구현 기능 |
| --- | --- |
| 구매자 | 회원가입·로그인, 검색·필터, AI 추천 챗봇, 상품 상세·다국어 안내, 달력 예약, 미성년 여부 선택, 데모 결제, 계약 알림, 웹 전자서명, 예약·서명 조회 및 취소 요청 |
| 판매자 | 판매자 등록·로그인, 상품 등록·수정·삭제, 사진 업로드, 예약 알림, AI 계약서 추천, 템플릿 선택 또는 직접 작성, 계약 검토·발송·재발송, 서명 상태·취소 요청 관리 |
| AI 파이프라인 | Upstage Solar Pro 3 추천·요약·번역, Document Parse 계약서 OCR·구조화, Information Extract 핵심 조항 추출, 개인정보 마스킹과 결과 캐시 |
| 전자계약 | 모두싸인 템플릿 기반 초안, Secure Link, 임베디드 서명, 발송·진행·완료 상태 조회, 완료 문서 보관·조회 |

## AI 활용 증빙 요약

| 기능 | 모델·API | 입력과 결과 | 코드 위치·장애 대응 |
| --- | --- | --- | --- |
| 맞춤 상품 추천 | Upstage Solar Pro 3 | 사용자 조건과 점수 상위 후보 5개 → 추천 상품 3개, 이유와 주의사항 | `POST /api/recommendations`, 실패 시 코드의 점수 기반 추천 |
| 상품 약관 점검 | Upstage Solar Pro 3 | 환불·예약·안전 약관 → 환불 주의사항과 불리할 수 있는 조항 | `POST /api/contract-summary`, 실패 시 규칙 기반 요약 |
| 실제 계약서 분석 | Document Parse → Information Extract → Solar Pro 3 | 모두싸인 PDF → 요금·기간·환불·안전·보상·책임 구조화 → 쉬운 위험 설명 | `POST /api/signature/contract-summary`, 개인정보 마스킹·문서별 캐시, 실패 시 원문 확인 안내 |
| 다국어 지원 | Solar Pro 3 | 상품·약관·계약서 원문 → 영어·일본어·중국어 | `POST /api/product-translation`, `POST /api/signature/contract-translation`, 실패 시 한국어 원문 유지 |
| 판매자 계약 추천 | Solar Pro 3 + 서버 안전 규칙 | 상품 조건과 예약자의 미성년 여부 → 적용할 모두싸인 템플릿 조합 | `POST /api/seller/contract-recommendations`, 실패 시 규칙 기반 추천 |

모델 설정, 프롬프트 규칙, 입력 제한, 개인정보 보호, 캐시와 대체 동작의 상세 내용은 [AI 사용 기록](docs/AI_USAGE.md)에 있습니다.

결제 화면은 사용자 흐름을 보여주기 위한 데모이며 실제 금액이 결제되지 않습니다.

## 빠른 실행

### 1. 준비 환경

- Node.js 20 이상
- npm
- 의존성 설치를 위한 인터넷 연결
- 전체 AI·전자서명 테스트 시 Upstage와 모두싸인 API 인증 정보

### 2. 저장소 내려받기

최신 구현은 `develop` 브랜치에 있습니다.

```bash
git clone --branch develop --single-branch https://github.com/hijin8216/AI-Builder-Sprint.git
cd AI-Builder-Sprint
npm install
```

Windows PowerShell에서 npm 실행 정책 오류가 나면 `npm.cmd install`을 사용합니다.

### 3. 환경변수 만들기

Windows PowerShell:

```powershell
Copy-Item .env.example .env
```

macOS 또는 Linux:

```bash
cp .env.example .env
```

생성된 `.env`에 필요한 값을 입력합니다. API 키 없이도 상품 탐색, 회원가입, 로컬 점수 기반 추천, 저장된 약관의 규칙 기반 요약과 판매자 상품 관리 화면은 확인할 수 있습니다.

### 4. 서버 실행

```bash
npm start
```

Windows PowerShell에서 실행 정책 오류가 나면 다음 명령을 사용합니다.

```powershell
npm.cmd start
```

접속 주소:

- 구매자 화면: <http://127.0.0.1:3000>
- 판매자 화면: <http://127.0.0.1:3000/seller>
- 서버 상태: <http://127.0.0.1:3000/api/health>

정상 실행 시 상태 API가 `status: "ok"`를 반환합니다. 서버 종료는 실행한 터미널에서 `Ctrl+C`를 누릅니다.

## 실행·배포 환경 정보

| 항목 | 내용 |
| --- | --- |
| 실행 방식 | Node.js 단일 로컬 서버 |
| 백엔드 | Express 5, `server.js` |
| 프론트엔드 | HTML, CSS, JavaScript 정적 파일 |
| 패키지 설치 | npm (`pnpm-lock.yaml`은 팀 개발 환경의 고정 버전 기록) |
| 기본 포트 | `3000`, `PORT`로 변경 가능 |
| 데이터 저장 | `data/*.local.json`, `data/seller-uploads.local/` |
| 외부 통신 | `api.upstage.ai`, `api.modusign.co.kr`에 HTTPS 연결 필요 |
| 클라우드 의존성 | 없음. AWS·Supabase 등 외부 DB를 사용하지 않음 |
| 현재 제출 방식 | 배포 주소가 아닌 README의 로컬 실행 가이드로 재현하는 방식 |

로컬 JSON 저장 방식은 해커톤 데모를 위한 구조입니다. 다중 서버 운영이나 동시 접속이 많은 실제 서비스에서는 DB, 영구 세션 저장소, 파일 스토리지로 교체해야 합니다.

## 환경변수

| 변수 | 필수 여부 | 용도 |
| --- | --- | --- |
| `UPSTAGE_API_KEY` | 전체 AI 기능 테스트 시 필수 | Solar Pro 3, Document Parse, Information Extract 호출 |
| `MODUSIGN_EMAIL` | 실제 전자서명 시 필수 | 모두싸인 API 키를 발급한 워크스페이스 이메일 |
| `MODUSIGN_API_KEY` | 실제 전자서명 시 필수 | 모두싸인 API 인증 |
| `MODUSIGN_SIGNER_ROLE` | 선택 | 템플릿의 서명자 역할을 자동으로 찾지 못할 때 역할 이름 지정 |
| `PORT` | 선택 | 서버 포트, 기본값 `3000` |

모두싸인 계정은 `data/contract-templates.json`에 등록된 템플릿을 소유하거나 접근할 수 있어야 합니다. 다른 계정에서 발급한 API 키를 쓰면 템플릿 조회 권한 오류가 날 수 있습니다.

`.env`는 `.gitignore`에 포함되어 있습니다. 실제 키, 비밀번호, 개인정보를 README·코드·커밋에 넣지 않습니다. 전체 전자서명 테스트용 모두싸인 환경변수는 저장소가 아니라 안내된 이메일로 별도 전달하고, 대회 종료 직후 테스트 키를 폐기합니다. Upstage API 키는 주최 측에 따로 보내지 않습니다.

## 테스트 계정과 로컬 데이터

저장소에는 공용 아이디나 비밀번호를 넣지 않습니다. 처음 실행한 환경에서는 화면에서 직접 계정을 만듭니다.

- 구매자: 우측 상단 `로그인` → `회원가입`
- 판매자: `/seller` → `판매자 등록`
- 전자서명 이메일을 확인하려면 실제로 받을 수 있는 이메일을 사용합니다.
- 구매자와 판매자를 동시에 테스트하려면 일반 창과 시크릿 창 등 서로 다른 브라우저 세션을 사용합니다.

계정, 예약, 판매 상품, 계약 발송 기록과 업로드 이미지는 아래 로컬 파일에 저장되며 GitHub에는 올라가지 않습니다.

- `data/users.local.json`
- `data/reservations.local.json`
- `data/seller-posts.local.json`
- `data/seller-contracts.local.json`
- `data/seller-uploads.local/`

서버를 재시작하면 보안을 위해 로그인 세션은 종료되지만 위 파일에 저장된 데이터는 유지됩니다.

## 재현 가능한 데모 시나리오

### API 키 없이 확인

1. 구매자 화면에서 지역·종목 필터와 상품 정렬을 확인합니다.
2. `AI 맞춤 추천`에서 동행, 분위기, 활동, 지역, 경험, 수영 여부, 예산과 나이를 입력합니다.
3. Solar를 사용할 수 없을 때도 로컬 점수 기반 추천 3개가 표시되는지 확인합니다.
4. 상품 상세에서 소개, 전체 약관, 다국어 화면과 규칙 기반 약관 요약을 확인합니다.
5. 회원가입 후 날짜·시간·인원·미성년 여부를 선택하고 데모 결제를 완료합니다.
6. 마이페이지에서 예약 내역과 취소 요청 흐름을 확인합니다.
7. 판매자 등록 후 상품 작성·수정·삭제와 예약 목록 화면을 확인합니다.

### Upstage·모두싸인 전체 흐름

1. 구매자 계정과 판매자 계정을 각각 다른 브라우저 세션에 준비합니다.
2. 판매자가 상품을 등록하고, 구매자가 해당 상품을 예약해 데모 결제를 완료합니다.
3. 판매자 화면의 새 예약 알림에서 계약 초안을 엽니다.
4. `AI 추천 계약서`, `템플릿 직접 선택`, `계약서 직접 작성` 중 한 방식을 선택합니다.
5. 미성년 예약에서는 법정대리인 동의서가 필수 추천되는지 확인합니다.
6. 판매자가 계약 내용을 검토·수정한 뒤 최종 서명 요청을 보냅니다.
7. 구매자 웹 알림과 이메일에 계약 요청이 도착하는지 확인합니다.
8. 구매자가 실제 계약서의 AI 요약·번역을 참고하고 모두싸인 임베디드 화면에서 서명합니다.
9. 구매자 마이페이지와 판매자 계약 현황에서 완료 상태와 체결 문서를 확인합니다.
10. 서명 완료 후 구매자 취소는 즉시 삭제가 아니라 판매자 검토가 필요한 취소 요청으로 처리되는지 확인합니다.

## API 오류와 대체 동작

| 상황 | 처리 방식 |
| --- | --- |
| Solar 응답 실패·시간 초과 | 상품 점수 기반 추천 또는 저장 약관의 규칙 기반 요약으로 전환 |
| 상품 번역 실패 | 한국어 원문 또는 내장 번역을 유지 |
| Document Parse·Information Extract 실패 | 실제 계약서를 분석했다고 표시하지 않고 원문 확인을 안내 |
| 모두싸인 인증 정보 누락 | 전자서명 단계에서 필요한 환경변수를 안내하고 기존 예약·초안은 유지 |
| 모두싸인 `403` | API 사용량, 워크스페이스와 템플릿 접근 권한 확인 안내 |
| 모두싸인 `429` | 한 번 지연 재시도 후 재시도 가능 안내 |
| 서명자 역할 탐색 실패 | `MODUSIGN_SIGNER_ROLE` 설정 안내 |
| 서버 재시작 | 저장 데이터는 유지하고 로그인만 다시 요구 |

## 전자계약 상태 처리

현재 로컬 데모는 공개 웹훅 주소가 없으므로 구매자 화면에서 약 30초마다 상태를 확인하고, 판매자 화면에서도 새로고침 API로 모두싸인 상태를 동기화합니다.

`초안 → 검토·수정 → 최종 서명 요청 → 서명 진행 → 완료 → 보관·조회`

실서비스 배포 시에는 모두싸인 완료 웹훅을 추가해 폴링을 보완해야 합니다. 문서에서는 구현되지 않은 웹훅을 구현 완료로 표시하지 않습니다.

## 현재 한계

- 실제 결제 API는 연결하지 않았으며 결제 화면은 데모입니다.
- 로컬 저장소는 운영용 DB가 아니며 여러 서버 인스턴스의 데이터 동기화를 지원하지 않습니다.
- 로그인 세션은 메모리에 있어 서버 재시작 시 다시 로그인해야 합니다.
- 실제 전자서명은 유효한 모두싸인 테스트 계정, API 사용량과 템플릿 접근 권한이 필요합니다.
- 로컬 환경에서는 모두싸인 완료 웹훅 대신 상태 조회 방식으로 동기화합니다.
